## 0. TL;DR + the one scope decision that needs a human ruling

This is Phase 3's cutover: retire the Compare *UI surface*, its *REST routes*, its *Compare-only business logic*, and its `activePage:"compare"` branch; redirect `/compare*` → `/series`; add the migrated-DB `rebuild_views_from_log!` round-trip test. **HEADLINE OPEN DECISION (frontend — needs a human ruling): removing `"compare"` empties the `PageId` union — who kills the `activePage` model, I3.6 or I5.1?** Per the orchestrator's 2026-05-27 correction (from I3.5b/PR #213 execution), the union is **2-WAY, not 3-way**: I3.5b did NOT add `"series"` to `PageId` (the whole series stage is CorpusShell, which never mounts `useStateFromUrl`/`useUrlFromState` — verified: those hooks live only in `AppShell.tsx`). So the only union editors are I4.4 (drops `"index"`) and I3.6 (drops `"compare"`). I rebase after I4.4, inheriting `PageId = "compare"` (one member; I4.4 parked the `coerceActivePage` fallback + initial `activePage` on `"compare"`). **When I remove `"compare"` the union becomes empty (`never`)** — and at that point all three legacy AppShell pages are cut (inspect ✅ I1.7, index ← I4.4, compare ← me), so the entire `activePage` model is vestigial. A zero-member `PageId` breaks `coerceActivePage` / the default / the initial store value.
- **Option A (RECOMMENDED — plan-supported):** I3.6 removes the `"compare"` branch/route/parser arm and leaves a coherent *degenerate placeholder* (union narrowed to a harmless single sentinel literal that nothing renders, e.g. `PageId = "none"` with the fallback returning it, OR keep the now-empty machinery typed-but-unreached) and **defers the model's death to I5.1 (#182)** — which is explicitly scoped to "delete… the Zustand `activePage` model, the nav-bridge" with acceptance "no `activePage` references remain", and is the very next issue. This keeps I3.6 a *cutover* (matching its "direct" card) and avoids pulling Phase-5 work forward. The I4.4 plan's own forward-compat note anticipates exactly this seam.
- **Option B:** removing `"compare"` forces pulling I5.1's `activePage`-model removal into I3.6 (delete `PageId`/`VALID_PAGE_IDS`/`coerceActivePage`/the model + nav-bridge now). Larger blast radius, overlaps I5.1's scope, and `AppShell`/`TabRocker`/`WorkspaceGrid` (also I5.1) still depend on the model so a partial removal is awkward.
- **My read:** Option A. I3.6 ends with a compiling, never-reached degenerate union + a `// I5.1 (#182) deletes this model` marker; I5.1 finishes it. I will implement A unless the human picks B. (This supersedes the earlier "PageId has no members; delete it" wording inherited from the I4.4 forward-compat note — that note predates the 2-way correction and conflated I3.6's narrowing with I5.1's deletion.)

**BLOCKING OPEN DECISION (backend — needs a human ruling before execution): `comparisons.jl` cannot be deleted wholesale.** The issue text + master plan §6.3 both say "delete `comparisons.jl`". That is **unsafe as written** and contradicts the "dispatcher branches stay forever" constraint. Verified by grep:

This honors the *intent* (Compare logic gone) while not breaking replay. **Alternative the human may prefer:** make zero deletions inside `comparisons.jl` this issue (delete only `routes_comparisons.jl`) and let I5.3's dead-code sweep remove the now-unreferenced route-only functions — lower risk, defers the cleanup. ## 5. The headline deliverable — migrated-DB `rebuild_views_from_log!` round-trip test

**Goal:** prove a series row *born from migration* (not native creation) folds correctly through the pure-replace dispatcher branches. Distinct from I2.7's native round-trip.

**Fixture → migrate → empty → re-fold → assert** (templates: `test_migrate_comparisons_to_series.jl` for the build+migrate; `test_routes_series.jl` native round-trip for the empty+refold+assert shape; `rebuild_views_from_log!(db, entity_id; entity_type="series")` signature at `events.jl:1034`):

1. **Build a real comparison-era DB:** `db = SQLite.DB(); create_schema!(db); migrate_schema!(db)`. Insert a user; insert a `comparisons` row (title/description/content_hash/created_by/created_at) + 2-3 `comparison_members` (real exposure FKs — reuse the existing migrate test's fixture builder so the FK graph is valid) + a `comparison_messages` row + a `comparison_pins` row. This is the pre-migration corpus.
   - **Subtlety:** `migrate_schema!` already runs `migrate_comparisons_to_series!` once (it's in the sequence). So I must insert the comparison rows and then invoke `migrate_comparisons_to_series!(db)` AFTER — but the sentinel gate makes the in-sequence run a no-op on an empty corpus and blocks a second run. **Resolution:** build the comparison rows on a DB where I run `create_schema!` + the migration-sequence-minus-the-final-migration, OR (cleaner) insert comparisons, then DELETE the sentinel row (`schema_migrations WHERE name = MIGRATION_COMPARISONS_TO_SERIES`), then call `migrate_comparisons_to_series!(db)` directly so it actually folds. Mirror exactly how the existing `test_migrate_comparisons_to_series.jl` "non-empty corpus" testset arranges this (read it at execution — it must already solve the sentinel-ordering, since it tests a non-empty migration).
2. **Capture migrated state:** read the resulting `series`/`series_members`/`series_samples` rows for the migrated `series_id` (the `series_*` view rows the dispatcher wrote during migration).
3. **Empty the view rows:** `DELETE FROM series_members WHERE series_id=?; DELETE FROM series_samples WHERE series_id=?; DELETE FROM series WHERE id=?` (or set to empty — match the native test's "empty" semantics; the `user_actions` log rows are NOT deleted — they are the source of truth to re-fold from).
4. **Re-fold:** `rebuild_views_from_log!(db, series_id; entity_type="series")`.
5. **Assert equality:** rebuilt `series`/`series_members`/`series_samples` rows deep-equal the captured migrated state (same membership, ordering, recipe, title/description, hash). Plus: the two synthesized `user_actions` (`series_created`, `series_plate_committed`) are unchanged; messages/pins (NOT view rows; verify whether rebuild touches them — likely not, they're copied not event-sourced) are untouched.
