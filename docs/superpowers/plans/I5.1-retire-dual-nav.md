## 1. What I5.1 actually is

Per master plan §8 and issue #182, retire the **dual-navigation scaffolding**:
delete the old `AppShell` shell body, `WorkspaceGrid`, `TabRocker`, the Zustand
`activePage` model, and the **nav-bridge**. After this, the app is a single shell
(CorpusShell). Acceptance: all four new surfaces still reachable; **no `activePage`
references remain in the codebase**.

The phase-5 critical-path order is `I3.6 → I5.1 → I5.2 → I5.3`. I3.6 deliberately
left the `activePage` model alive as the inert `"none"` sentinel (narrowing the
union would have made `PageId` a zero-member `never`, breaking `coerceActivePage`).
I5.1 is where the sentinel, the model, `coerceActivePage`, `VALID_PAGE_IDS`, and the
dead Zustand→URL bridge all finally die.

### The one non-obvious structural fact (the headline risk)

The `*` catch-all is currently mounted **inside the `<AppShell>` layout route**
(`AppRoutes.tsx:125–127`). AppShell renders four things: `<AppHeader/>`,
`<TabRocker/>`, `<Outlet/>` (→ `PageBody` → StaleUrlPage / ResolvingFallback), and
`<NavModal/>`. The catch-all + StaleUrlPage are the **permalink stale-URL system**,
NOT the dual-nav model — they must survive I5.1. So deleting AppShell is not a pure
deletion: the `*` catch-all (PageBody/StaleUrlPage) and the chrome it currently
shows (`AppHeader` + `NavModal`) must be **re-homed**, not deleted.

Decision (see §5): re-home the `*` catch-all under the existing `<CorpusShell>`
layout route. CorpusShell already renders `<CorpusTopbar/>` + `<Outlet/>`. This keeps
StaleUrlPage reachable and gives it consistent corpus chrome. `AppHeader` + `NavModal`
+ `TabRocker` are then orphaned (their only render site was AppShell) — grep-gated
below to confirm before deleting.

## 4. The persist boundary — what I deliberately leave to #183

Issue #182 scope says **"Leave the persist-version bumps to #183."** Master plan §2.3
warns: a `persist` `version` bump **without** a `migrate` callback **wipes every user's
persisted state**. The store has no `migrate` today (`version: 3`, only a `merge`).

**The reconciliation problem:** Deleting the `activePage` field from `AppState` means
the `partialize` line `activePage: s.activePage` (L688) no longer compiles, and the
`merge`'s `coerceActivePage(merged.activePage)` line (L706) no longer compiles. But
#183 owns "remove `activePage` from `partialize` + bump version with a migrate."

**Resolution (the boundary):**
- I5.1 **removes** the `activePage: s.activePage` line from `partialize` and the
  `activePage` coercion line from `mergePersistedState` — these are forced by deleting
  the field and are mechanical, not a version change.
- I5.1 does **NOT** bump `version` (stays `3`) and does **NOT** add a `migrate`.
  **Why this is safe without a migrate:** a persisted blob from a pre-I5.1 client still
  carries an `activePage` key. After I5.1, `mergePersistedState` does
  `{...current, ...persisted}` — the stale `activePage` key lands in `merged` but is
  simply an **unread extra property** (no field reads it, no `partialize` re-persists
  it on the next write, so it ages out naturally on the next state mutation). It does
  not crash, does not wipe prefs (`username`/`theme`/`tutorialSeen` survive the shallow
  merge untouched). This is the "missing/extra keys read undefined" additive-safety
  principle (§2.3) applied in reverse — an extra key is inert.
- #183 then does the **deliberate** `version` bump + `migrate` that formally strips the
  dead `activePage` key from old blobs (cosmetic cleanup + the queue `schema_version`
  bump for stale `comparison_*` ops). That bump is #183's job precisely because it needs
  a `migrate` to not wipe state — out of scope here.

**Net:** I5.1 touches `partialize`/`merge` only to keep the file compiling after the
field deletion, with **no version bump and no migrate**. This is the documented seam
(§2.3: "Phase 5's removal of activePage from partialize is the one warranted bump +
migrate" — that warranted bump is #183, not #182). Reviewer should confirm this reading;
if the reviewer judges that removing the `partialize` line itself constitutes the
#183-owned change, the fallback is to leave `activePage: s.activePage` referencing a
**retained-but-renamed** legacy key — but that is uglier and I do not recommend it.
**This is open question OQ-1 (§7).**

## 5. Re-homing the catch-all + URL-sync hook (the structural change)

AppShell's deletion orphans: (a) the `*` catch-all route, (b) the `useStateFromUrl`
mount, (c) `AppHeader`, (d) `NavModal`.

**Plan:**
1. **Catch-all** → move `<Route path="*" element={<PageBody/>}/>` into the existing
   `<Route element={<CorpusShell/>}>` block in `AppRoutes.tsx`. StaleUrlPage then renders
   inside CorpusShell's `<Outlet/>`, under `CorpusTopbar`. PageBody/ResolvingFallback/
   StaleUrlPage imports unchanged.
2. **`useStateFromUrl` mount** → it must run on the catch-all so it can classify the
   stale path. Two options:
   - (a) Call `useStateFromUrl()` inside `CorpusShell` (it now hosts the catch-all). But
     CorpusShell also hosts `/samples`, `/series`, `/sample/:id` — running the stale
     classifier there is fine (those paths match real routes, so `parseLocation` returns
     `root` only on bare `/` which is already redirected; non-matching paths hit `*`).
     Need to verify the classifier doesn't mis-flag a valid corpus route as stale —
     **it won't, because `useStateFromUrl` only runs `setStaleUnknownPath` when the route
     it's mounted under is the `*` catch-all** … except mounting it in CorpusShell means
     it runs on ALL corpus routes. **Risk:** on `/samples`, `parseLocation("/samples")`
     returns `{kind:"stale"}` (parseLocation has no `/samples` arm!), which would wrongly
     park `/samples` on StaleUrlPage. **This is the trap.** → Reject option (a).
   - (b) **Mount `useStateFromUrl()` inside `PageBody`** (the `*` catch-all element
     itself), not in any layout shell. PageBody is rendered only on the catch-all, so the
     classifier runs only there — preserving today's "only runs on the stale path"
     isolation that AppShell provided. This is the minimal, behavior-preserving move.
     **Choose option (b).** PageBody becomes a small component that calls
     `useStateFromUrl()` then renders StaleUrlPage/ResolvingFallback off `staleUrlContext`.
3. **`NavModal`** → re-home to `App.tsx` (always-mounted, alongside `SeriesCommitConflictModal`/
   `OnboardingFlow`). It is opened by `/`, `⌘K`, and StaleUrlPage recovery from anywhere,
   so app-wide mounting is correct.
4. **`AppHeader` + `UtilityCluster`** → **OQ-2 RESOLVED: delete both now** (§2a/§2g).
   Their only render site was AppShell; CorpusTopbar already owns the equivalent chrome.
   No re-home. The stale page wears `CorpusTopbar` via the re-homed catch-all.
