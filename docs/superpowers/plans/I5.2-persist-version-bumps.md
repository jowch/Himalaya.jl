## 1. Goal

Two **independent** persisted-state version counters get a deliberate bump, each with the
correct discard/preserve semantics:

1. **Zustand `persist` `version`** (`state.ts`) — bump **with a real `migrate`** that strips
   the dead `activePage` key while preserving `username` / `theme` / `tutorialSeen` (and the
   rest of the partialized blob). Without a `migrate`, a `version` mismatch makes Zustand
   **discard the entire persisted blob** — the wipe risk.
2. **Queue `SCHEMA_VERSION`** (`lib/queue/persistence.ts`) — bump so any pre-cutover queued
   `comparison_*` (and any other) op left in `sessionStorage` **drops cleanly as a toast**,
   not via a `mutatorRegistry` throw or a replay against a now-dead backend route.

These two counters are unrelated subsystems and must not be conflated. Both are bumped on purpose.

**In scope (verbatim from #183 / master plan §8 lines 247–248):**
- `state.ts`: confirm `activePage` is gone from `partialize` (I5.1 already did this); bump
  `persist` `version` **with a real `migrate`**.
- `lib/queue/persistence.ts`: bump the queue `SCHEMA_VERSION` (independent counter).
- Vitest both.

**Out of scope:** dual-nav deletion (#182, I5.1, done); the dead-code sweep + build gate
(#184, I5.3). The `comparison_*` REPLAY machinery (the `saveComparison` / `deleteComparison` /
`postComparisonMessage` mutators, their registry arms, the `applyRemoteToCache` arms) is
**KEPT FOREVER** for historical/migrated SSE logs — do **not** touch it (master plan §2.1,
risk table line 266).

- **`version` is `3`** — `src/state.ts:661` (`version: 3`).
- **No `migrate` callback today** — the `persist` options object (`src/state.ts:653–673`)

- **`partialize`** (`src/state.ts:662–671`) already persists exactly the 8 allow-listed keys
  and **does NOT include `activePage`** (I5.1 removed it; comment at `state.ts:655–660`).
  → The first acceptance bullet ("`activePage` gone from `partialize`") is **already satisfied**;
  I5.2 reconciles it (verifies + removes the now-obsolete "version stays 3" comment) and adds
  the formal `migrate`.
  Persisted keys: `username`, `firstName`, `lastName`, `activeExperimentId`,
  `activeSampleId`, `activeExposureId`, `tutorialSeen`, `theme`.
- **`merge`** is the named export `mergePersistedState` (`src/state.ts:672`, defined
  `state.ts:682–687`): shallow `{ ...current, ...(persisted as Partial<AppState>) }`.
- **Zustand version: `4.5.7`** (`package.json` declares `^4.5.0`; installed `4.5.7`).

**Migrate/merge ordering in zustand v4** (verified against the v4.5 persist middleware): on
rehydrate the pipeline is **`deserialize` → `migrate(persistedState, version)` → `merge(migrated, currentState)`**.
`migrate` runs **first** and transforms the *stored* blob; `merge` runs **after** and folds the
migrated blob over the live default state (which carries the store actions). So:
- `migrate` only needs to return the **persisted data shape** (the partialized keys), minus
  `activePage`. It must NOT try to reconstruct actions — `merge` supplies those via `...current`.
- `migrate` only fires when the stored `version` **differs from** the configured `version`.
  A fresh store (no stored blob) skips `migrate` entirely (no `persistedState`).

### 2.2 Queue persistence (`src/lib/queue/persistence.ts`)

- **`SCHEMA_VERSION` is `2`** — `src/lib/queue/persistence.ts:7` (`export const SCHEMA_VERSION = 2;`),
  with the history comment at `:6` ("Bumped 1 → 2 in issue #88: sample.label dropped, …").
- **Stale-op behavior today** (`persistence.ts:114–122`, the rehydrate loop):
  ```
  for (const op of ops) {
    if (op.schemaVersion !== SCHEMA_VERSION) { dropped++; continue; }   // :115–118
    const mutator = lookup(op);
    if (!mutator) { dropped++; continue; }                              // :120–122
    …onMutate / request / onSuccess…
  }
  ```
  So a persisted op is dropped (counted in `dropped`, no mutator touched) when **either** its
  `schemaVersion` mismatches **or** `resolveMutator` returns `undefined`.

  **CRITICAL distinction — what a stale queued `comparison_*` op does TODAY (SCHEMA_VERSION
  still 2, op stored as schemaVersion 2):**
  - `resolveMutator` (`mutatorRegistry.ts:119–121`) **still maps `comparison_save` →
    `saveComparisonMutator` and `comparison_delete` → `deleteComparisonMutator`** — these arms
    are KEPT. So the op does **not** hit the `!mutator` drop and does **not** throw in the
    registry.
  - Instead it **replays as a real mutation**: `onMutate` patches the cache optimistically,
    then `request` fires `POST`/`DELETE /api/comparisons…`. Against a post-cutover backend
    (Compare routes retired by I3.6 #177), that request **404s**, the `.catch` rolls back
    (`persistence.ts:146–154`), and it lands in **`failed`** → the "edits failed to replay;
    please retry" **error** toast (`App.tsx:81–86`) — a misleading message for an op that can
    never succeed. (NOTE: `saveComparisonMutator.onMutate` is a **no-op** with
    `restore: () => {}` — `saveComparison.ts:81` — so there is **no** optimistic cache patch and
    **no** rollback flicker; the only observable defect is the spurious 404 → error toast.)

  So the bug being fixed is precise: a pre-cutover queued `comparison_*` op should drop as a
  benign **warning** toast ("couldn't be restored"), not 404-fail as an **error** toast.

- **What bumping `SCHEMA_VERSION` 2 → 3 changes:** every op persisted before the bump carries
  `schemaVersion: 2`, so on the next rehydrate it hits the `op.schemaVersion !== SCHEMA_VERSION`
  guard (`persistence.ts:115`) and is counted in **`dropped`** — **before** `lookup`/`onMutate`/
  `request` ever run. No optimistic patch, no 404, no rollback, no registry throw. `dropped > 0`
  surfaces the **warning** toast (`App.tsx:74–80`). This is the desired "drops as a toast, not a
  `mutatorRegistry` throw / 404-error" behavior, and it drops **all** stale kinds uniformly
  (correct — the whole pre-cutover queue is suspect after a deploy, not just `comparison_*`).
- The `STORAGE_KEY` is cleared after rehydrate (`persistence.ts:160`), so the dropped ops do not
  linger to re-drop on the next reload.

## 3. The `migrate` callback — exact shape

**From → To:** Zustand `persist` `version` **`3` → `4`**.

Add a `migrate` to the `persist` options object (`state.ts:653–673`). It receives the
deserialized stored blob (the partialized keys, possibly carrying a dead `activePage`) and the
stored version number, and returns the cleaned **persisted-data** shape. It must NOT fabricate
store actions — `mergePersistedState` (the `merge`) supplies those afterward via `...current`.

Proposed shape (final wording settled at execute time; semantics fixed here):

```ts
// state.ts persist options
{
  name: LS_KEY,
  version: 4, // 3 → 4 (I5.2 #183): formally strip the dead `activePage` key.
  partialize: (s) => ({ /* unchanged 8 keys; activePage already absent */ }),
  migrate: (persisted, _version) => {
    // Any pre-v4 blob may still carry a dead `activePage` key (I5.1 #182
    // removed the field but held version at 3, letting it age out). Strip it
    // here and pass the surviving prefs through verbatim. We deliberately do
    // NOT hard-code a from-version branch: the only transform across every
    // prior version is "drop activePage", and returning the blob minus that
    // key is safe for v1/v2/v3 alike. `merge` (mergePersistedState) re-attaches
    // the store actions afterward, so we return ONLY persisted data.
    //
    // WIPE-GUARD (OQ-3, queue/frontend reviewer hardening): the else-branch
    // returns `persisted` UNTOUCHED — never `{}`/`undefined`. A non-object /
    // malformed blob handed `{}` (or undefined) here is the ONLY way this
    // migrate could itself partial-wipe prefs; returning the original lets
    // `merge` fold whatever survived (or nothing, falling back to defaults)
    // without the migrate destroying data it couldn't parse.
    if (persisted && typeof persisted === "object") {
      const { activePage: _activePage, ...rest } = persisted as Record<string, unknown>;
      return rest as AppState;
    }
    return persisted as AppState;
  },
  merge: mergePersistedState,
}
```

Key properties the reviewers should confirm:
- **Preserves prefs:** `username` / `theme` / `tutorialSeen` (and `firstName` / `lastName` /
  `activeExperimentId` / `activeSampleId` / `activeExposureId`) flow through untouched in `...rest`.
- **Strips the dead key:** `activePage` is destructured out, so it can no longer ride along as an
  inert extra property (which is what I5.1 left it doing via shallow merge).
- **No wipe:** returning a value (not `undefined`) means Zustand keeps the migrated blob; `merge`
  then folds it over the live defaults.
- **Idempotent / version-agnostic (OQ-3, LOCKED):** no `_version` branching — "drop `activePage`"
  is the only transform and is safe for any prior version. Reviewers confirmed: keep the
  unconditional strip; YAGNI on a `switch (version)` scaffold. The one hardening they required is
  the malformed-blob wipe-guard above (else-branch returns `persisted`, never `{}`/`undefined`).
- **Type / cast (OQ-2, LOCKED):** the `migrate` signature in zustand v4 is
  `(persistedState: unknown, version: number) => S | Promise<S>`. Cast the return **`as AppState`**
  (both branches), mirroring `mergePersistedState`'s existing `as Partial<AppState>` cast at
  `state.ts:686`. This keeps **`npm run build`** (src tsc) green — the gate. (Bare `npx tsc`'s
  ~183 test/ errors are pre-existing and NOT the gate — memory: himalaya-frontend-bare-tsc-dirty.)

**Comment reconciliation:** the I5.1 explainer comments at `state.ts:655–660` and `:677–681`
both say "version stays 3 / NOT bumped here — #183 does it." I5.2 rewrites these to reflect the
v4 + migrate reality (the migrate is now the formal strip).
**NIT (frontend reviewer):** the `:677–681` block is the JSDoc on `mergePersistedState` itself —
only its "version stays 3" *reference* is stale. `mergePersistedState`'s behavior does NOT change
(it stays the shallow `{ ...current, ...persisted }` merge). When rewriting, update only the
version reference; do NOT imply the merge function itself changed.
