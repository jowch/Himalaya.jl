# I3.4 — Series Scoping UI Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build the series scoping step at `/series/new` — the "machine proposes / human confirms" surface that reads corpus tags to propose an ordering variable, lets the user confirm a parsed `(key,value)` per member sample, and on confirm writes those tags via the existing batch route with `source='scoping'`, then navigates to the builder draft.

**Architecture:** A new `/series/new` page under the CorpusShell layout route. It reads `GET /api/sample-tags` (corpus, to propose the ordering variable) and `GET /api/picker-samples` (corpus, the member candidates), renders a worksheet of `(sample → parsed value)` rows with a focus-trapped confirm modal, and on "Confirm & build" issues **one** `POST /api/samples/tags/batch` (one `key`, N `{sample_id, value}`, `source='scoping'`) through a **queue-routed** mutation (no-op `onMutate`, like `saveSeriesMutator`), then `navigate("/series/new")`'s sibling builder entry. The batch route (I2.6, merged) already accepts `source` — **no backend change** (re-audit below).

**Tech Stack:** React 18 + TS strict (`exactOptionalPropertyTypes`), react-router-dom v6, TanStack Query, the mutation queue (`useQueueMutation` + a new no-op-optimistic mutator + `client_op_id`), `useFocusTrap`, Vitest + RTL, Playwright (mocked).

**Issue:** #174 (I3.4). Depends on I3.2, I2.6, I0.2, I0.3 (all merged). Unblocks I3.6. Detailed plan (new surface + structured-tag contract). **Queue-routed → queue-reviewer applies** (see "Queue routing" below).

## I2.6 batch-route re-audit (the contract scoping writes through)

Audited `packages/HimalayaUI/src/routes_samples.jl` `@post "/api/samples/tags/batch"` on `origin/main` @ 4d4f9c6. **Shape is exactly what scoping needs — no drift, no in-PR widening required.**

- **Request body:** `{ key: string (required), tags: [{ sample_id: int, value: string }] (required, non-empty), source?: string }`.
- **`source`** defaults to `"manual"`; **scoping passes `"scoping"`** — first-class supported (`source = haskey(body, :source) ? String(body.source) : "manual"`), and the column is `sample_tags.source`.
- **Structured `(key,value)`:** one `key` per batch (the ordering-variable name), each entry carries its own `value` (the parsed value). This is exactly the issue's contract: "key = the ordering-variable name, value = the parsed value." ✓
- **Atomicity:** one `with_idempotency` transaction → N `sample_tags` INSERTs + N `add_tag` events, all commit/rollback together.
- **Validation (all pre-transaction → clean 400):** body must be an object; `key` string; `tags` non-empty vector; each entry `{sample_id:int, value:string}`; **duplicate `sample_id` in one batch → 400** (they'd collide on `idx_events_unique_op` since all events share one `client_op_id`). Scoping must therefore send **at most one entry per sample** (it does — one row per member sample).
- **Response:** `201` with `[{ id, sample_id, key, value, source }]`.
- **Idempotency:** `with_idempotency` keys on the `X-Client-Op-Id` header; without it `f` runs once with no dedup cache. Scoping **sends** a `client_op_id` (queue-routed) so a retry is idempotent.
- **No frontend caller exists yet** — `api.ts` has no batch-tags function. This plan adds it.

**Drift verdict: NONE.** If a future need to write *different keys in one batch* arises, that's a route change → fast-follow, not this PR. Scoping writes one ordering-variable key per series, so one-key-per-batch fits.

## Queue routing decision (for queue-reviewer)

**The scoping write IS queue-routed** through `useQueueMutation` with a dedicated mutator, **NOT a plain mutation.** Rationale, grounded in `lib/queue/AGENTS.md` + `docs/mutation-queue.md`:

- The batch route is built on `with_idempotency` and **emits `add_tag` SSE frames** — it is a multiplayer write. Other clients' corpus caches (`samples`, `sample-tags`) must invalidate on the foreign event; the queue's `client_op_id` keying is what drives own-op confirmation vs. foreign-event replay. A plain `fetch` would bypass that contract.
- **No optimistic patch is needed** — on success the user *navigates away* to the builder; there is no in-place tag view on the scoping surface to optimistically mutate and roll back. So the mutator's `onMutate` is a **no-op `restore`**, exactly mirroring `saveSeriesMutator` (`onMutate: () => ({ restore: () => {} })`). This is the established "leaves-the-surface, multiplayer-visible, no optimistic write" pattern.
- **N events / one client_op_id:** the batch emits N `add_tag` frames sharing the single `client_op_id` minted by `useQueueMutation`. Own-op confirmation matches the first frame and clears the deferred; subsequent same-op frames are self-echoes (dropped, no duplicate). This is the multiplayer-replay contract the queue already implements — the plan adds a Vitest contract test pinning it (Task 6).

**Implication:** the orchestrator should add **queue-reviewer** to this PR's review set.

import type { SampleTagPair, PickerSampleRow } from "../../api";

export interface OrderingRow {
  sampleId: number;
  sampleName: string;
  value: string;
  flagged: boolean; // true when the sample has no value for the ordering key
}
export interface OrderingProposal {
  orderingKey: string | undefined; // undefined on a cold corpus
  rows: OrderingRow[];
}

/**
 * Machine proposal for the series ordering variable. Picks the most frequent
 * tag `key` across the corpus tag pairs as the ordering variable, then reads
 * each member sample's value for that key. A sample missing the key is
 * `flagged` (the human must resolve it before the confirm-and-build gate
 * opens). Cold corpus (no tags) → no key, every row flagged (#174 accepts
 * this — scoping starts cold).
 */
export function proposeOrdering(
  corpusTags: SampleTagPair[],
  samples: PickerSampleRow[],
): OrderingProposal {
  const freq = new Map<string, number>();
  for (const t of corpusTags) freq.set(t.key, (freq.get(t.key) ?? 0) + 1);
  let orderingKey: string | undefined;
  let best = 0;
  // Deterministic: highest count, ties broken by lexicographic key.
  for (const [key, count] of [...freq.entries()].sort((a, b) =>
    b[1] - a[1] || (a[0] < b[0] ? -1 : 1))) {
    if (count > best) { best = count; orderingKey = key; }
    break;
  }
  const rows: OrderingRow[] = samples.map((s) => {
    const tag = orderingKey === undefined
      ? undefined
      : s.sample.tags.find((t) => t.key === orderingKey);
    const value = tag?.value ?? "";
    return {
      sampleId: s.sample.id,
      sampleName: s.sample.display_name ?? s.sample.name,
      value,
      flagged: value === "",
    };
  });
  return { orderingKey, rows };
}
```

import type { Mutator, RollbackContext } from "../types";
import type { AuthOpts } from "../../../api";
import { authOpts } from "../../authOpts";
import { queryKeys } from "../../../queries";
import * as api from "../../../api";

export interface ScopeSeriesInput {
  key: string;
  tags: { sampleId: number; value: string }[];
}
export interface ScopeSeriesScope { username: string | undefined; clientId: string }

// Local auth-opts wrapper — same pattern every mutator file uses (saveSeries,
// saveComparison, trivial, …): wrap the shared authOpts(username, clientId,
// clientOpId) so request() reads the op's metadata off the flat payload.
function buildAuthOpts(p: { username: string | undefined; clientId: string; clientOpId: string }): AuthOpts {
  return authOpts(p.username, p.clientId, p.clientOpId);
}

/**
 * scopeSeriesMutator — series scoping's batch sample_tags write (#174).
 * Queue-routed for `client_op_id` idempotency + multiplayer SSE, but with a
 * NO-OP onMutate: on success the user navigates to the builder, so there is no
 * on-surface tag view to optimistically patch/roll back (mirrors
 * saveSeriesMutator). The batch route emits N `add_tag` frames sharing this
 * op's single client_op_id; own-op confirmation matches the first, the rest
 * self-echo (dropped). onSuccess invalidates the corpus tag + samples caches
 * so a returning user sees the written tags.
 */
export const scopeSeriesMutator: Mutator<ScopeSeriesInput, ScopeSeriesScope, api.BatchSampleTagResult[]> = {
  kind: "add_tag",
  onMutate: (): RollbackContext => ({ restore: () => {} }),
  request: (p) =>
    api.batchSampleTags(
      p.key,
      p.tags.map((t) => ({ sample_id: t.sampleId, value: t.value })),
      "scoping",
      buildAuthOpts(p),
    ),
  onSuccess: (_p, _response, qc) => {
    qc.invalidateQueries({ queryKey: queryKeys.corpusSampleTags });
    qc.invalidateQueries({ queryKey: queryKeys.corpusPickerSamples });
    // Per-sample tag rows live in the corpus samples cache; blast it.
    qc.invalidateQueries({ queryKey: ["experiment"] });
  },
  // Foreign replay: a peer's scoping batch arrives as add_tag frames. We hold
  // no optimistic state, so the SSE-wins path just needs a non-undefined
  // response to route through onSuccess (which only invalidates). `base` is
  // QueueResponseMeta, not BatchSampleTagResult[]; cast as saveSeries does for
  // its partial-Series SSE shape — onSuccess ignores the response body here.
  synthesizeFromSse: (_remote, base) => base as unknown as api.BatchSampleTagResult[],
};
```
