# I3.5b (#176) — Series builder mutations — DETAILED PLAN

Status: **plan, awaiting human approval.** No production code or tests written yet.
Branch: `i3.5b` (worktree `.claude/worktrees/i3.5b`, off `origin/main` @ `22d0d6f`).

## 0. One-paragraph summary

Wire the *mutation* layer onto I3.5a's read-only `SeriesBuilderPage` (`/series/:id`).
A committed series becomes editable via a local **series draft** (Zustand,
sessionStorage-mirrored, mirroring the comparison draft machinery exactly).
Recipe edits (membership: add/remove/reorder samples, ordering-variable,
order-rule) are **optimistic** — they flush through the already-merged
`saveSeries` mutator (`series_save` → `series_recipe_updated`) and the optimistic
state lives in the draft, with **negative `series_samples` placeholder ids minted
by `nextOptimisticId()`** for not-yet-persisted recipe rows. The plate commit
(turn the recipe into a frozen plate) is **spinner** — no optimistic write — and
flushes through the already-merged `commitSeriesPlate` mutator (`series_commit` →
`series_plate_committed`, which carries the `post_state` envelope). Figure export
already round-trips on the read surface; we keep it working in edit mode. **Conflict
handling is COMMIT-ONLY**: recipe-save (`PATCH`) never reads `expected_content_hash`
and never 409s, so only the plate commit can conflict; a commit 409 surfaces through
a **shared-chrome ConflictModal** (chrome extracted; Compare + series each own their
semantics). Permalink: make `/series/:id` a recognized (non-stale) URL that the page
owns via `useParams`/`useNavigate`, exactly like Compare's numeric-id URL-ownership
pattern.

## 2. Architecture decisions (call out for human / reviewers)

### D1 — Series draft mirrors the comparison draft, in a NEW namespace

The comparison flow keeps an `activeDraft: ActiveDraft | null` in Zustand
(sessionStorage-mirrored via `withDraftMirror`), built by `fromComparison` /
`emptyDraft`, edited by `setDraftTitle` etc. I will mirror this for series with a
**separate** `seriesDraft` slot — NOT reuse `activeDraft`. Rationale: `activeDraft`
is `Comparison`-shaped (members carry comparison snapshots, fork lineage,
`compareXDomains` keyed by comparison id). A series recipe edits **`series_samples`
membership** (sample_id, position, pinned, excluded) — a different shape — and a
series *commit* produces **`series_members`** (the plate). Overloading one slot
risks the two flows clobbering each other in sister tabs. New slot, parallel
machinery, sessionStorage key `himalaya:series-draft`.

`SeriesDraft` shape (new `src/lib/series/seriesDraft.ts`):
```ts
interface SeriesRecipeRow {
  // negative when not-yet-persisted (nextOptimisticId); positive = server id
  id: number;
  sample_id: number;
  position: number;
  pinned: boolean;
  excluded: boolean;
}
interface SeriesDraft {
  id: number;                 // the series being edited (always an existing id)
  title: string;
  description: string;
  orderingVariable: string | null;
  orderRule: OrderRule;
  recipe: SeriesRecipeRow[];  // the editable membership
  baseHash: string | undefined; // content_hash seen at load → expected_content_hash
}
```
**Key client-state invariant (master plan §11):** never key client state on
`series_samples.id`. The recipe rows are keyed by `(series_id, position)` for
reconciliation and by their (possibly-negative) `id` only for local React keys.
Placeholder ids from `nextOptimisticId()` are local-only; they are **stripped**
when building `SeriesSampleInput[]` for the wire (the input type has no `id`
field — membership is positional). This is *why* the recipe-edit cache arm is
invalidate-only and ids are replay-volatile: the optimistic id is a render-key,
not an identity sent to the server.

### D2 — Recipe = optimistic, Commit = spinner (per issue / master plan §6.2)

- **Recipe edit** (`useSaveSeries` → `series_save` → `series_recipe_updated`):
  optimistic. The optimism is delivered by the **draft** (the user sees their
  edits in `seriesDraft` immediately, with negative-id placeholder rows for
  newly-added samples). The mutator itself does no optimistic cache write
  (`onMutate` is the no-op `{ restore: () => {} }` already shipped) — the draft is
  the optimistic surface. On success the cache arm invalidates and the next read
  refetches the canonical projection (which re-keys the recipe rows to real ids);
  the draft is then discarded or rebased. This matches `saveSeries`'s docstring:
  "No optimistic write — the builder UI (I3.5b) shows the local draft." **Recipe
  save sends NO `expected_content_hash`** — `PATCH /api/series/{id}`
  (routes_series.jl:170-214) never reads it; the field is absent from
  `SaveSeriesBody`. Recipe save therefore **cannot 409 / conflict.**
- **Plate commit** (`useCommitSeriesPlate` → `series_commit` →
  `series_plate_committed`): spinner. No optimistic write; a pending flag on the
  button; on success `post_state` is spliced into the detail cache by the merged
  arm and `useSeries` re-renders the committed plate.

### D3 — ConflictModal reuse: RESOLVED → D3a via chrome-extraction (COMMIT-ONLY)

Resolved by both reviewers to **D3a** (literal "reuse," issue-map L251), implemented
the way the frontend-reviewer scoped it: **extract the shared chrome into a
presentational shell** — do NOT bolt an `if (kind === "series")` branch onto the
existing dense, deeply-Compare-coupled monolith (that risks the Compare path).

Today: `pendingConflict: ConflictError | null` where
`ConflictError.current_state: Comparison | null`; the modal reads `activeDraft`,
calls `discardDraft` + `goToReview` (compare paths), rebuilds via
`buildOverwritePayload` from a comparison draft. Compare-coupled end to end.

Implementation:
1. **Extract `ConflictModalShell`** (new `src/components/ConflictModalShell.tsx`) —
   presentational only: the dialog frame, `useFocusTrap`, Esc handler, the footer
   buttons, and the `overwriteInFlightRef` double-click guard. Props are slots
   (title, server-state panel, the discard/overwrite handlers + labels + a
   `saving` flag). No `activeDraft`/`useSaveComparison` knowledge.
2. **Compare keeps its semantics** — the existing `ConflictModal` becomes a thin
   wrapper that supplies the comparison-specific handlers (discard → `/compare`,
   overwrite via `buildOverwritePayload` + `useSaveComparison`) to the shell.
   **Behavior byte-for-byte unchanged** (regression-guarded by existing tests).
3. **Series gets a thin wrapper** — `SeriesCommitConflictModal` supplies
   series-specific handlers: discard → navigate `/series/:id`; overwrite rebuilds a
   `CommitSeriesPlateBody` from `seriesDraft` against the server `current_hash`,
   re-flushing `useCommitSeriesPlate`. **Commit-only** — there is no recipe-save
   conflict path.
4. **Widen `ConflictError.current_state` to `Comparison | Series | null`** (no
   discriminator needed — each wrapper knows its own kind by where it's mounted /
   which slot it reads). The Comparison `conflictBridge` write behavior is unchanged
   (see must-fix below).

### D4 — Permalink: ALREADY COMPLETE via CorpusShell — NO URL-hook / PageId work

**EXECUTION-TIME CORRECTION (supersedes the plan's earlier D4).** During the
rebase audit I verified that `useStateFromUrl`/`useUrlFromState` mount **only in
`AppShell`** (AppShell.tsx:28-29) — the legacy Index/Compare shell. The series
builder is mounted under **`CorpusShell`** (AppRoutes.tsx:99-112), which does
**NOT** mount those hooks at all. The other CorpusShell surfaces (`/samples`,
`/series`, `/series/new`, `/sample/:id`) confirm this: `parseLocation` has no
`samples` or `series` arm, yet they aren't stale-flagged — because the URL hooks
never run for CorpusShell routes. `activePage` is `"index" | "compare"` only and
is never set to `"series"` (CorpusTopbar navigates via plain react-router
`<Link to="/series">`, not `setActivePage`).

**Consequence:** the `parseLocation` arm, the `VALID_PAGES`/`VALID_PAGE_IDS`/
`coerceActivePage` widening, the `PageId` `| "series"`, and the
`useStateFromUrl`/`useUrlFromState` series branches from the earlier plan would
all be **dead code** — those hooks never see a `/series/*` URL. I will NOT write
them.

`/series/:id` is therefore **already a fully URL-owned permalink**: react-router
`useParams<{id}>` reads it, `useNavigate` writes it (cancel/post-commit), copy-link
copies `window.location.href`, paste/reload re-fetches via `useSeries`. This is the
*completed, stronger* form of the URL-ownership pattern the issue points to (cleaner
than Compare, which still needs the AppShell hooks to set `activePage`). **No
permalink code is needed for I3.5b.** The figure-export/permalink round-trip is
exercised by the e2e spec (copy-link → reload → re-render), not by new hook code.

**This also eliminates the I4.4 file-collision entirely** (see D5).

### D6 — Where edit controls live

`SeriesBuilderRail`'s docstring reserves "add sample, reorder commit,

## 4. Queue invariants honored (master plan §11, Phase 3)

1. **Negative `series_samples` placeholder ids via `nextOptimisticId()`** — minted
   in the series-draft add action; local render-keys only; stripped before the wire.
2. **Replay-volatile `series_samples.id`** — client state keyed by
   `(series_id, position)`, never by `series_samples.id`. The recipe-edit cache arm
   stays invalidate-only (no splice). Verified the merged arm already does this.
3. **`series_recipe_updated` wholesale-replace** — we do NOT add a surgical splice;
   the merged invalidate-only arm is correct and untouched.
4. **`content_hash` folds the plate only / `""` while draft** — the draft's
   `baseHash` is the series' `content_hash` at load; sent as `expected_content_hash`
   **on commit only** (recipe-save's `PATCH` never reads it); a draft series
   projects `content_hash === ""`.
5. **`client_op_id` minted inside `mutationFn`** — comes for free from
   `useQueueMutation`; each Save/Commit/Overwrite click mints a fresh op id.
   Double-click guards (an in-flight ref) on commit + overwrite, per the
   ConflictModal precedent (queue-reviewer Fix 3).
6. **Own-op confirmation / foreign-event replay-as-rerun** — unchanged; the merged
   `applyRemoteToCache` arms + `resolveMutatorForEvent` already cover all 4
   view-producing series kinds. We add no new event kinds.
7. **JSON-only idempotent replay** — series routes are already JSON-only; we add
   no binary responses.
