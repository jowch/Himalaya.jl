# I1.6 — Contact-Sheet Culling Wiring Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Wire exposure culling into the contact sheet — single reject toggle, multi-select batch reject, and representative-exposure pick — all round-tripping through the mutation queue via the existing `useSetExposureStatus` / `useSelectExposure` / `useAddExposureTag` hooks.

**Architecture:** `ContactSheetRow` already owns its per-sample `useExposures(sample.id)` query. We make the inert `ExposureThumb` interactive and add a per-row multi-select model plus a small action bar. All writes go through the three existing queue hooks — no new mutators, no new routes, no new API functions. The batch-reject path is **N sequential single-exposure ops**, not one batch op: each `setStatus.mutate(...)` mints its own `clientOpId` and applies its own per-exposure optimistic patch to the shared `queryKeys.exposures(sampleId)` cache, so the patches compose without a new batch mutator. This resolves issue #162's open question ("Whether batch reject issues N queued ops or one") in favor of **N ops** — the existing optimistic-update machinery already handles it correctly and the I1.6 card explicitly says "use existing hooks."

**Tech Stack:** React 18 + TypeScript (strict, `exactOptionalPropertyTypes`), TanStack Query, the HimalayaUI mutation queue (`useQueueMutation`), Vitest + React Testing Library, Playwright (mocked).

**Issue:** #162 (I1.6). Depends on I1.4 (contact sheet UI — done). Unblocks I1.7 (Inspect cutover). Direct issue — this plan is lightweight by design (the hooks exist; the work is wiring + state).

### Optimistic-update semantics (load-bearing for the batch path)
From `packages/HimalayaUI/frontend/src/lib/queue/mutators/trivial.ts`:

- **`setExposureStatusMutator`** (`kind: "set_exposure_status"`): `onMutate` patches the one exposure in the `queryKeys.exposures(sampleId)` list cache (`e.id === p.exposureId ? { ...e, status: p.status } : e`) and the single-exposure cache, returning a `restore` closure for rollback. Per-exposure, so **N independent calls compose** — exposure A and exposure B each get their own patch and their own rollback.
- **`selectExposureMutator`** (`kind: "select_exposure"`): `onMutate` writes `selected: e.id === p.exposureId` across the whole list — i.e. **mutually exclusive** representative pick. This gives "one representative per sample" for free; picking B un-picks A optimistically.
- Each `useQueueMutation.mutate()` mints a fresh `clientOpId` inside the call (`useQueueMutation.ts:118-130`), so issuing N reject mutations enqueues N independently-keyed, independently-confirmed, independently-rollback-able ops. **This is the correct batch behavior; do not build a batch mutator.**

### `Exposure` shape (`api.ts:129-135`)
```ts
export interface Exposure {
  id: number; sample_id: number; filename: string; kind: ...;
  selected: boolean;
  status: "accepted" | "rejected" | null;
  ...
}
```
Rejected ⇔ `status === "rejected"`. Toggling reject back to accepted in the loupe uses `status: null` (see `LoupePage.handleDropToggle` — `status === "rejected" ? null : "rejected"`). **Match that convention** so behavior is consistent across surfaces.

### Test strategy — real hooks vs. mocked hooks (deliberate)

`LoupePage.test.tsx` mocks `../queries` (`vi.mock`) so the hooks return a stub `{ mutate, isPending, ... }` and asserts the handler *calls* `mutate`. This plan instead drives the **real** `useSetExposureStatus` / `useSelectExposure` through a `fetch` spy + `QueryClientProvider`, because #162's acceptance criterion is "round-trips through the queue" — we want to prove the op actually reaches `PATCH /api/exposures/:id/...` and the optimistic patch lands in the `useExposures` cache, not merely that a stub was invoked. `renderRow` already provides `QueryClientProvider`; `useAppState` is a Zustand module singleton (no provider needed), matching how the existing `ContactSheetRow` tests run. **Fallback:** if the queue's durable-persistence side-effects (IndexedDB/localStorage under JSDOM) make these tests flaky, fall back to the LoupePage `vi.mock("../queries", ...)` strategy — assert `setStatusMutate`/`setRepMutate` call args — which still satisfies the three-interaction Vitest requirement. Prefer the real-hook path; switch only on demonstrated flakiness.

## Multi-select state model

Local to `ContactSheetRow` (each row is independent — selection does not cross sample boundaries, matching the per-sample query fan-out):

```ts
const [selectedIds, setSelectedIds] = useState<ReadonlySet<number>>(new Set());

const toggleSelected = useCallback((id: number) => {
  setSelectedIds((prev) => {
    const next = new Set(prev);
    next.has(id) ? next.delete(id) : next.add(id);
    return next;
  });
}, []);

const clearSelection = useCallback(() => setSelectedIds(new Set()), []);
```

- A thumb is "selected for batch" when `selectedIds.has(exposure.id)` → drives `data-batch-selected` on the thumb for test/Playwright targeting.
- The action bar shows when `selectedIds.size > 0`: a "Reject N selected" button and a "Clear" button.
- After a batch reject fires, call `clearSelection()` (optimistic patches already moved the rows to rejected; keeping them selected would be confusing).
- Reset selection if the exposure list identity changes is **not** required — TanStack keeps stable ids across refetch; stale ids in the set are harmless (the batch handler filters to currently-present, non-rejected exposures before mutating).

### Three handlers

```ts
const setStatus = useSetExposureStatus(sample.id);
const setRepresentative = useSelectExposure(sample.id);

// Single reject toggle (one thumb's reject affordance).
const handleToggleReject = useCallback((exp: Exposure) => {
  setStatus.mutate({
    exposureId: exp.id,
    status: exp.status === "rejected" ? null : "rejected",
  });
}, [setStatus]);

// Batch reject — N independent ops, one per currently-kept selected exposure.
const handleBatchReject = useCallback(() => {
  for (const exp of exposures) {
    if (selectedIds.has(exp.id) && exp.status !== "rejected") {
      setStatus.mutate({ exposureId: exp.id, status: "rejected" });
    }
  }
  clearSelection();
}, [exposures, selectedIds, setStatus, clearSelection]);

// Representative pick (mutually exclusive via the mutator's onMutate).
const handlePickRepresentative = useCallback((exp: Exposure) => {
  setRepresentative.mutate(exp.id);
}, [setRepresentative]);
```

> **Why iterate `exposures`, not `selectedIds`:** guarantees stable order, lets us filter out already-rejected exposures (no redundant op), and skips stale ids not in the current list.
