# I4.1 — Focus-workspace route-to-Zustand wiring shim — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add a `/sample/:sampleId` route under the new corpus shell whose route parameter drives the Zustand `activeSampleId`, so the reused index components (`PlotCard` / `IndicesCard` / `PhasePanel`) — which read `active*Id` directly from the store — render correctly under a URL-routed surface, without yet touching the still-live `/index` surface.

**Architecture:** A thin **route-param→Zustand sync** (chosen over prop-drill — see *Decision* below). A new pathless-free `<Route path="/sample/:sampleId">` is registered under the existing `CorpusShell` layout route in `AppRoutes.tsx`. Its element is a new `FocusWorkspacePage` that, for I4.1, contains only a `useSyncActiveSampleFromRoute()` hook (the shim) plus a minimal placeholder body; I4.2 (#179) fills in the real trace-hero/detector/phase-rail layout. The shim reads `useParams().sampleId`, validates it against the corpus-samples cache, and pushes it into the store via the existing `setActiveSample` action — guarded so it fires only on change (to avoid clobbering the cascade that `setActiveSample` triggers). No `state.ts` field is added in I4.1; the existing `activeSampleId` field + `setActiveSample` action already exist and are reused.

**Tech Stack:** React 18, react-router-dom v6 (`useParams`, `Route`), Zustand (`useAppState`, named actions), TanStack Query (`useCorpusSamples`), Vitest + React Testing Library + `MemoryRouter`, TypeScript strict + `exactOptionalPropertyTypes`.

## Decision: route-param→Zustand sync (NOT prop-drill), and rationale

The issue (#178) and dispatch-plan §4 require picking **one** of two approaches. We pick **route-param→Zustand sync**.

**Why not prop-drill.** `PlotCard`, `IndicesCard`, and `PhasePanel` each call `useAppState((s) => s.activeSampleId)` / `s.activeExposureId` internally (verified: `useGlobalShortcuts.ts` reads/writes `activeSampleId` via the store, `useAutoPickExposure.ts` derives `activeExposureId` from the store, and `useUrlFromState.ts` reflects both back to the URL). Prop-drilling `sampleId` would require:
- changing all three component signatures to accept a `sampleId` prop **and** threading it past every intermediate component, and
- either deleting their Zustand reads (which would break the still-live `/index` surface that drives them through `activePage`/Zustand — out of scope for I4.1, forbidden until I4.4) **or** maintaining two parallel data paths in the same components.

That is exactly the "three reused components" risk the issue map flags. Prop-drill maximizes blast radius and breaks the I4.4 "no-cutover-yet" constraint.

**Why sync.** A one-way `URL → setActiveSample(store)` sync keeps the three components reading from Zustand **unchanged** (regression floor for I4.2 is "carried-over trace/index interaction tests must pass unchanged"). It mirrors the established `useStateFromUrl` pattern already in the codebase and the precedent set by `LoupePage` at `/samples/loupe/:sampleId` (URL-owned sample id). The difference from `LoupePage`: `LoupePage` keeps its sample id purely local (`useParams` → local consumption) because it owns standalone child components; the focus workspace instead reuses Zustand-coupled components, so the route param must be *published into the store* rather than consumed locally.

**Forward-compatibility with the Phase-4 chain.**
- **I4.2 (#179):** fills `FocusWorkspacePage`'s body; the shim hook stays the single source that seeds `activeSampleId` from the URL.
- **I4.3 (#180):** adds the ephemeral `hoveredQ` field — additive to `state.ts`, excluded from `partialize`; independent of this shim.
- **I4.4 (#181):** retires `IndexPage` + `activePage:"index"`. At that point the shim is the *only* path that sets `activeSampleId` on the focus surface; nothing here needs to change for the cutover, and we deliberately add a forward-compatible bidirectional note (below).

**One-way vs two-way (a deliberate scoping decision).** I4.1 ships a **one-way** URL→store sync only. Reflecting store→URL (the reverse direction, so a `,`/`.` sample-step keypress rewrites `/sample/:id`) is **not** required for I4.1's acceptance ("the route param drives `activeSampleId`") and would re-introduce the `useUrlFromState` `resolving`-handshake complexity that the corpus shell was specifically structured to avoid (see `AppShell.tsx` comment: the new shell "owns its own URL and the legacy stale-path logic cannot strand the user there"). The reverse direction is owned by I4.2/I4.4 when the in-page navigation affordances land. **Open decision for the human** is recorded at the end.

## Background the implementer needs (read before starting)

1. **`setActiveSample` cascades.** In `state.ts`:
   ```ts
   setActiveSample: (activeSampleId) =>
     set({ activeSampleId, activeExposureId: undefined, staleUrlContext: null }),
   ```
   It clears `activeExposureId`. This is why the shim MUST call it **only when the id actually changes** — calling it on every render would wipe the exposure that `useAutoPickExposure` just selected, causing a flicker/refetch loop. This guard is load-bearing, not cosmetic.
2. **The corpus cache.** `useCorpusSamples()` (in `queries.ts`, used by `LoupePage`) returns `CorpusSample[]` from `GET /api/samples`, each with a numeric `id`. Validate the route param against this list so a bogus `/sample/999999` does not seed a non-existent id into the store. While the cache is still loading, do nothing (the effect re-runs when it resolves).
3. **Route params are strings.** `useParams<{ sampleId: string }>()` yields a string; `Number(...)` + `Number.isFinite(...)` is the established validation idiom (see `LoupePage.tsx:70-71`).
4. **`CorpusShell` already exists** and is the layout-route element for new corpus surfaces (`AppRoutes.tsx:98`). The `/sample/:sampleId` route belongs **inside** that `<Route element={<CorpusShell />}>` block, alongside `/samples` and `/samples/loupe/:sampleId`, NOT inside the legacy `<AppShell>` block.
5. **Test conventions** (`frontend/test/AGENTS.md`): reset the `useAppState` singleton in `beforeEach` (`useAppState.setState(...)` + `localStorage.clear()`); prefer RTL queries + `data-testid` over `document.querySelector`; use the JSDOM `fetch` interceptor pattern for `useCorpusSamples`; wrap router-dependent renders in `MemoryRouter`.

```ts
import { useEffect } from "react";
import { useParams } from "react-router-dom";
import { useAppState } from "../state";
import { useCorpusSamples } from "../queries";

/**
 * useSyncActiveSampleFromRoute — the I4.1 focus-workspace wiring shim.
 *
 * Maps the `/sample/:sampleId` route parameter onto the Zustand
 * `activeSampleId`, so the reused index components (PlotCard / IndicesCard /
 * PhasePanel — which read `active*Id` directly from the store, not from props)
 * render correctly under the URL-routed focus surface (issue #178 / I4.1).
 *
 * One-way (URL -> store). The reverse direction (store -> URL on in-page
 * sample stepping) is owned by I4.2/I4.4 when the focus surface gains its own
 * navigation affordances; reflecting it here would re-introduce the
 * `useUrlFromState` resolving-handshake the corpus shell was built to avoid.
 *
 * The id is validated against the corpus-samples cache so a bogus deep-link
 * (`/sample/999999`) never seeds a non-existent id. `setActiveSample` is
 * called ONLY when the id actually changes, because that action cascades
 * `activeExposureId: undefined` — calling it every render would clobber the
 * exposure `useAutoPickExposure` just selected.
 */
export function useSyncActiveSampleFromRoute(): void {
  const { sampleId: sampleIdParam } = useParams<{ sampleId: string }>();
  const corpusQ = useCorpusSamples();
  const activeSampleId = useAppState((s) => s.activeSampleId);
  const setActiveSample = useAppState((s) => s.setActiveSample);

  useEffect(() => {
    const parsed = Number(sampleIdParam);
    if (!Number.isFinite(parsed)) return; // non-numeric param: ignore
    const samples = corpusQ.data;
    if (samples === undefined) return; // cache not ready yet; re-runs on resolve
    if (!samples.some((s) => s.id === parsed)) return; // unknown sample: ignore
    if (parsed === activeSampleId) return; // no-op: avoid the exposure-clobber cascade
    setActiveSample(parsed);
  }, [sampleIdParam, corpusQ.data, activeSampleId, setActiveSample]);
}
```

## Open decisions for the human (do not block the plan)

1. **One-way only?** I4.1 syncs URL→store but not store→URL. So if some future in-page control calls `setActiveSample` while on `/sample/:id`, the URL will not follow until I4.2/I4.4 add the reverse reflection. Confirm this is acceptable for the shim (the issue's acceptance only requires the forward direction). If the human wants the reverse now, it is a separate, larger change (resolving-handshake) and should be its own task.
2. **Bogus-id UX.** I4.1 silently ignores an unknown/non-numeric `:sampleId` (store stays `undefined`, placeholder renders). `LoupePage` instead shows a "Sample not found" panel. We deliberately defer the not-found UX to I4.2 (it belongs with the real layout). Confirm "silent ignore + placeholder" is fine for the shim-only milestone.
3. **Route name.** Dispatch plan says `/sample/:sampleId` (singular), distinct from the existing corpus `/samples` and `/samples/loupe/:sampleId`. Plan uses `/sample/:sampleId` verbatim. Confirm no collision concern with a future `/samples/:id` (none today).
