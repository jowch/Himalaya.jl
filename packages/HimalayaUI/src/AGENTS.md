## SQLite.jl

- **`DBInterface.lastrowid` takes the query *result*, not the db**: `res = DBInterface.execute(db, sql, params); id = Int(DBInterface.lastrowid(res))`.
- **Raw rows from `DBInterface.execute` lose values after the query closes.** Materialize with `sqlrows(DBInterface.execute(...))` (`db_rows.jl`) to get stable `NamedTuple`s (access via `row.name`). Never `Tables.rowtable`: it types each column by the values it finds, so a NULL or an empty result makes a new row type, and every function that reads it compiles again on first use (about 0.8 s on the first sample open). `sqlrows` types a column from its declared SQL type (`Union{Missing, Int64/Float64/String}`), or `Any` for an expression column or a value that doesn't fit. `test_precompile_workload.jl` fails on any `rowtable` in `src/`.
- **`sqlrows` returns `missing` for SQL NULL, not `nothing`.** Use `ismissing(row.field)`; normalize to `nothing` when mixing with literals: `existing = ismissing(row.field) ? nothing : row.field`. `routes_users.jl` is the canonical NULL-fill example.
- **`samples.name` is auto-assigned at ingest and renamable.** `scan_and_group!` names each sample `<label> (SNNPMM)` (`_auto_name`, `grouping.jl`); a `name` in `PATCH /api/samples/:id` renames it and set `name_source = 'user'`. Rescans are insert-only, so they never overwrite a rename. The old `display_name` column was collapsed into `name` (`migrate_samples_name_collapse!`), and `name` is not unique within an experiment. Use the `sampleDisplayName(s)` helper everywhere in the frontend.
- **`exposure_sources.role` encodes two derived-exposure use-cases in one table** (`db.jl`): `role='signal'` alone = simple averaging; `role='signal'` + `role='background'` together = background subtraction. The single text-enum column is deliberate — a third provenance type extends it without a schema migration. (Derived-exposure construction itself is still a future feature.)
- **FK enforcement is on.** `open_db` runs `PRAGMA foreign_keys = ON` per connection. FKs that must survive user deletion need `ON DELETE SET NULL` in the schema DDL — at the column, not at call sites. `index_groups.created_by` and `user_actions.user_id` already have this.
- **`PRAGMA schema_version = N+1` requires `writable_schema = ON`** on most SQLite builds. Used as a VACUUM-free schema-cache invalidator; silently no-ops if `writable_schema` is off. The FK-heal fallback toggles it back on for the bump.
- **PKs use `AUTOINCREMENT` on entity tables** (`experiments`, `samples`, `exposures`, `auto_peaks`, `peak_curations`, `indices`). Plain `INTEGER PRIMARY KEY` is rowid-aliased and reuses freed ids, so a URL or `user_actions` row naming a deleted entity could rebind to a new one. `migrate_pk_to_autoincrement!` heals legacy DBs on next `open_db`. (The literal `_AUTOINCREMENT_ENTITIES` tuple still lists the removed `peaks` table purely for legacy-DB healing.)
- **New timestamps use `now_iso()`** (T-separator, ms, Z). Legacy `CURRENT_TIMESTAMP` (space-sep) survives in `user_actions.timestamp` — don't sort across the two formats as strings (issue #76).
- **`open_db` enables WAL + finalizes statements twice.** Every file-based DB gets `PRAGMA journal_mode = WAL` (skipped for `:memory:` and `file:` URIs) — a one-time persistent file-header change enabling concurrent readers + one writer, load-bearing for `parallel = true` request handling (#115). `open_db` calls `SQLite.finalize_statements!` twice: once after the DDL migrations (`migrate_schema!`), once after the WAL PRAGMA. Without them a cached prepared statement from a migration transaction can reference a dropped `_migrate_old_*` table and fail the first real query. Test harnesses that bypass `open_db` can hit intermittent "database is locked" / "no such table: main._migrate_old_*". See `db.jl::open_db`.
- **`_MIGRATION_TEMP_ENTITIES` carries a substring-uniqueness invariant.** `_fix_fk_references_after_autoincrement_migration!` heals FK refs via an UNANCHORED substring `REPLACE` on `sqlite_master.sql` for each `_migrate_old_<entity>` name in the tuple — safe ONLY because no entity name is a substring of another (adding `peak` while `peaks` exists would corrupt every `peaks` ref). The constant (`= (_AUTOINCREMENT_ENTITIES..., "index_peaks")`) must stay in lockstep with `migrate_pk_to_autoincrement!` and `migrate_r2_widen_index_peaks_pk!`; if you add an entity, re-check the invariant or anchor the replace. See `db.jl` (constant + heal loop).
- **A migration that adds a column filled from files must be backfilled from `start_background!`, not from a rescan (#333).** `migrate_exposures_beam_monitors!` adds the beam-monitor columns empty; `backfill_all_monitors!` fills them on a background task at every boot. `trace_median` (the beam-off reading) works the same way through `backfill_trace_medians!`. A pass only runs when an experiment is opened or has ingest work, so a quiet experiment is never rescanned. `serve` and the boot test both call `start_background!`, so add boot work there, not inline in `serve`.
- **Series, comparisons and sample chat were deleted (2026-11-21).** `migrate_drop_retired_tables!` drops their tables (`RETIRED_TABLES`) on every `open_db`; it is `DROP TABLE IF EXISTS`, so it is idempotent and needs no sentinel. Their `user_actions` rows stay in the log: `update_view_for_event!` returns early for them through one `RETIRED_EVENT_KINDS` guard, so `rebuild_views_from_log!` ignores them. The grouping-review kinds (`sample_renamed`, `sample_created`, `sample_split`, `grouping_flag_dismissed`) joined that list when grouping review was deleted (PR 384); `exposure_moved` still replays so historical moves survive a rebuild. Anything similar is rebuilt from scratch with a new design.

## Oxygen.jl 1.10.x

- Use the singleton API: `@get "/path/{id}" function(req::HTTP.Request, id::Int) ... end`. Typed function args extract path params.
- Parse JSON body with `json(req)` (unqualified, imported via `using Oxygen`), **not** `Oxygen.json(req)`.
- Test harness pattern: `Oxygen.resetstate()` before `Oxygen.serve(; async=true)`, `Oxygen.terminate()` after. A module-level `Ref{Union{SQLite.DB, Nothing}}` holds the live DB (matches the one-experiment-per-process model).
- Mount static files with `Oxygen.dynamicfiles(dir, "/")` — only if `isdir(dir)`, so empty frontends don't break tests.
- Oxygen emits a harmless warning about OpenAPI schema generation for some routes; ignore it.
- **Custom response headers are dropped on idempotency cache replay.** A route wrapped in `with_idempotency` that sets custom headers (`Cache-Control`, CORS, `X-Image-*`, …) replays only `Content-Type: application/json` on a cache HIT — the `idempotent_responses` row stores `status_code` + `body`, not headers. Silent, not an error. A new idempotent route needing custom headers must persist them in the cache schema or accept they vanish on retry. See `idempotency.jl::_lookup_cached_response`.
- **`parallel = true` is on** (#115). Every request handler dispatches across the worker thread pool — without it, all handlers stickied to tid=1 even with `JULIA_NUM_THREADS > 1`. Routes therefore must not assume cooperative single-threaded execution. Writers serialize at the Julia level via `_DB_WRITE_LOCK` (server.jl), a `ReentrantLock` acquired by every `SQLite.transaction(db)` site on the singleton: `with_idempotency` (both branches), the default `apply_event!`, `persist_analysis!`, `analyze_exposure!`, `suggest_labels_quietly!`, and the `gc_idempotent_responses!` DELETE. Closes #122 Race 1 (`SQLite.transaction` TOCTOU — loud 500s + silent savepoint nesting) and Race 2 writer-vs-writer (`db.stmt_wrappers` Dict mutation). Reentrant so a route body inside `with_idempotency` calling `analyze_exposure!` doesn't self-deadlock.

- **Connections (`db_connections.jl`).** `db_connection_middleware` runs on every request (production `serve`, `start_test_server!`, `with_inproc_routes`, the precompile workload). GET and HEAD read through a pooled `query_only` reader, so they never see another request's open transaction on the singleton (they did before: a GET during a write transaction returned rows that were then rolled back) and never wait for a writer under WAL. Every other request holds `_DB_WRITE_LOCK` from start to finish, so only one task at a time touches the singleton. A GET that writes fails loudly with `attempt to write a readonly database`; look up rows instead of creating them. `/api/events` keeps the singleton and never reads the DB. Work spawned off a request or timer (scans, rescans, the boot monitor backfill) outlives the request's lock, so it runs inside `with_background_db`, which opens its own connection. Its transactions still take `_DB_WRITE_LOCK`. In-memory DBs have no file to reopen and keep the singleton for everything.

## Cold start (precompile workload)

- **`precompile.jl` runs `run_route_workload` inside a PrecompileTools `@compile_workload`.** It builds a throwaway experiment in a temp dir, then drives every workspace route twice: in process (`Oxygen.internalrequest`) and over a real socket. Without it a restarted server spent ~35 s before answering and ~30 s more compiling on the first sample open and first edit (a first peak add took 17 s). With it: ~8 s boot, ~6 s of first-use compile in total. The rest is specializations on the real DB's row types, which a synthetic DB can't predict.
- **The cost moves to package precompile: ~100 s instead of ~5 s, every time `src/` changes.** Deploys must precompile (or `make sysimage`) before restarting; see "Updating a deployment" in `packages/HimalayaUI/README.md`.
- **Off for dev, on by default.** `make dev-setup` writes a gitignored `LocalPreferences.toml` next to `packages/HimalayaUI/Project.toml` with `[HimalayaUI]` / `precompile_workload = false` when none exists, then runs `make setup`; the CI test jobs write the same file. `make setup` (the deploy path) never writes it and ends with `Pkg.precompile()`, so a deploy keeps the warm-up. The demo-truth job has no file, so the real precompile path stays exercised. `test_precompile_workload.jl` (wire group) runs the workload at runtime, so a route change that breaks it fails a test, not a deploy.
- **Phases are type parameters, so the indexing and custom-index code is compiled once per phase.** The workload analyzes a second trace (`_workload_mixed_centers`) that holds peaks of every phase, and makes a custom index for each phase in `_WORKLOAD_PHASES`. Without it, the first edit on a sample with an uncommon phase mix compiled ~30 methods (~0.4 s). Don't splat a runtime-length vector into `push!(v, xs...)`: each element count and phase combination compiles its own method. Use `append!`. `test_precompile_workload.jl` fails if that trace stops yielding an index of every phase the pipeline searches, so a peak-finding retune can't quietly bring the per-phase stalls back.
- **Precompiled edit-route code is thrown away at load when anything it calls takes an abstract argument type that a later-loaded method can widen.** `JSON3.read(::AbstractString)` reached Parsers' `BigInt` path, which CEnum's `cconvert` method invalidates. As a result, 25 of 46 `with_idempotency` specializations recompiled on the first edit of each kind, at 0.1–0.5 s each. Pass concrete types (`JSON3.read(x::String)`, `replace(String(s), …)`). `scripts/check_precompile_cache.jl` (the required "Cold start" CI job) checks every concrete specialization of HimalayaUI, Himalaya and HimalayaPeakModel, not just the edit routes, fails when any is rejected and names them; `invalidation_trees(@snoop_invalidations using HimalayaUI)` from SnoopCompile finds the cause. A sysimage skips this check at load, so production on `make sysimage` only paid for the phase gaps.
- **A route that returns a plain Julia value (such as `rows_to_json`'s `Vector{Dict}`) goes through Oxygen's `format_response!`, which serializes with JSON.jl, and that cached code is thrown away at load too** (0.6 s on the first `GET /api/users`). Return `HTTP.Response(200, ["Content-Type" => "application/json"], JSON3.write(x))`.
- **`scripts/check_first_use.jl` holds a compile budget for the first use of each triage step** (boot and its background work, experiment load, first and second sample open, every edit) on a fresh server against the demo, in the same CI job. It clears the render cache first, so a sample open always renders. It counts only time spent compiling inside the server call, so harness code and machine speed matter little, and on a breach it lists the slowest methods that compiled in that step. The compile counter is process-wide: work the server starts in the background (the boot task, timers) must finish before a step is measured, or it is charged to that step. Run it locally with `prepare <demo root> <db>` once, then `julia --trace-compile=<file> --trace-compile-timing … measure <db>`; `FIRST_USE_BUDGET_SCALE=0` prints every step's compiles. Usual fixes: drive the route in the workload with data that reaches the same types (a `.prp`, monitors, every phase), `@nospecialize` a `Type{<:Phase}` argument whose body doesn't need it, or compare by `===` instead of hashing `Index{P}` values.
- **Every route is either in `_workload_requests` or in `_COLD_ROUTES_OFF_THE_TRIAGE_PATH`** (`test_precompile_workload.jl`). A new route fails that test until you pick one. A workload request that returns ≥300 throws, which fails precompile. That is deliberate: a silently skipped request would just bring the cold-start cost back.
- **The workload must leave no module state behind**, because module globals are serialized into the package image. `run_route_workload` saves and restores `_DB_REF`, `SSE_SUBSCRIBERS`, its own `OP_LOCKS` entries and the peak-set hash cache. The test compares every mutable `const` container in the module before and after, so a new cache the workload fills fails it.

## Pipeline + curation

- **`ANALYSIS_VERSION` (`pipeline.jl`) gates the hash fast path.** It is the core Himalaya version plus a local `+N`. An exposure whose `analysis_version` differs ignores its stored `trace_hash`/`analysis_inputs_hash` and is re-analyzed by the next pass, which `resume_ingests!` runs at boot. Bump `+N` when a HimalayaUI change alters analysis output without a core version bump. A NULL `analysis_version` means "unknown", so the exposure is re-analyzed; never stamp the current version on analyses the current code did not produce. Reviewed exposures (`reviewed_at` set) are exempt: a stale version never re-detects them, so curations, calls and assignments stay attached to the peaks the user saw. A failed analysis is stored in `analysis_error` with the current version and retried only after the version changes; `"no trace"` means the `_tot.dat` has not landed yet and is retried by every pass that finds it.
- **A phase call belongs to the sample, not a frame (#350).** State lives in `sample_calls`; members are the union of `assignment_members` over every frame of the sample, dropped ones included. Never derive a sample's call or status from the representative frame, and never clear members when a frame is dropped. See `docs/event-log.md` §"Phase calls belong to the sample".
- **`analyze_exposure!` curation contract.** Before calling `Himalaya.indexpeaks`, it calls `effective_peaks(db, exposure_id, q, I)` which synthesises `auto_peaks − peak_curations(kind='exclude') ∪ peak_curations(kind='add')`, with sharpness for adds sampled from `Himalaya.sharpness(I)`. Without this, exclusions don't affect scoring and manual peaks never land in `IndexEntry.peaks`. That raw value can be ≤ 0 on a shoulder, whereas the hybrid detector stores an auto peak with sharpness ≤ 0 as the median positive sharpness, so an add replacing such a peak can carry a different, even negative, sharpness. Touch only with curation-lifecycle regression tests in `test_pipeline.jl` green. See `docs/event-log.md` §1 for the auto/curation table split.
- **Curations attach to auto peaks only through `peak_matching.jl`.** Never write a new `ABS(c.q - a.q) <= …` join or a local `tol(q)`: use `peak_match_tol` (Julia; defined in `packages/HimalayaPeakModel/src/matching.jl` so the peak model's labels use the same rule, and imported into `peak_matching.jl`) or `curation_flags` / `peak_listing` (each curation attaches only to its nearest auto peak within tolerance). The tolerance is 6 grid points via `exposures.q_step`; a NULL step means the old `max(1e-6, 0.001·|q|)` rule. `effective_peaks`, `hash_peak_set_from_db`, `GET /peaks`, `_effective_peak_rows` and `diff_update_auto_peaks!` must agree, so change them together (`test_peak_matching.jl`). Curation `q` values are never rewritten on replay or re-detection.
- **`persist_analysis!` is transactional.** The auto-peak diff-update + index re-resolve sequence is wrapped in `SQLite.transaction`. New write steps must go inside `_persist_analysis_inner!` so they stay atomic. The ingestion path (`scan_and_group!` in `ingest.jl`) follows the same inner-transaction pattern.
- **`index_peaks.ratio_position` is the Julia↔DB round-trip contract for the index data model.** A core `Index{P}.peaks` is a `SparseVector` (`src/index.jl`); the slot index *is* the ratio-series position. Persist via `SparseArrays.findnz(idx.peaks)` → `(ratio_positions, peak_qvals)` written to `index_peaks` (`pipeline.jl`); the read path rebuilds the `SparseVector` from sorted `ratio_position`s. Any migration or rewrite of the persist/read path must preserve this slot identity or reconstruction breaks silently.
- **`speculative_peak_intents` is the durable record; `index_peaks` is a resolved view.** Analysis wipes and rebuilds `index_peaks` for speculatives every run, resolving from intents (creation-time ratio→q assignments, frozen, cascade-deleted with the index). Never write intents from discovery results **unless the index is `basis_locked`** (see below), and never let a failed re-resolution delete them — zero resolved peaks must leave the row `candidate` with empty `index_peaks` (do not write `status='stale'`; it's a dead enum normalized away on open).
- **`indices.basis_locked = 1` is what makes scan-derived intents legitimate.** The no-discovery-intents rule above exists for one reason: resolved intents feed `_persist_analysis_inner!`'s least-squares refit (`pipeline.jl`), so intents invented by a tolerance scan can drag an index's lattice somewhere the user never put it. `insert_custom_index!` (the custom-index modal) writes exactly such scan-derived intents — legitimately, because it also sets `basis_locked = 1`, and the pipeline skips the refit for locked rows: it re-resolves their peaks and recomputes score/R²/residuals **against the stored basis**, never solving for a new one. The invariant is therefore *intents may be scan-derived iff they cannot move the comb*. If you add another writer of scan-derived intents, it must lock the basis too — or the guarantee that a user-chosen lattice survives reanalysis silently dies.

  **The pipeline also skips its auto-discovery pass entirely for locked rows**, and that skip — not any persisted column — is what freezes a locked index's claim set. The commit bounds its claim to the reflections the modal *drew* (a ratio set, not a count; see `compute_snap`. Since #342 the frontend `SYMS.Ms` reads `frontend/src/lib/phaseRatioIndices.json`, which `test_speculative.jl` and `test_assignments.jl` check against core `phaseratios`, so a core series change must regenerate that file); discovery scans the whole core series, so re-enabling it for locked rows would let a reanalysis claim orders the user was never shown and make the rail's "explains N peaks" exceed the modal's "N of M land" again. It would also search against a comb refit from the resolved peaks — the very comb the locked row refuses to store. Re-resolution from intents can only ever reproduce a subset of what was drawn; nothing may re-widen it.

## Experiment config

The `setups` rows under an experiment are the configuration: `data_dir`, `analysis_dir`, the three file patterns, and geometry with per-field `*_source` (`setups.jl`). The experiment row keeps only `name`, `description`, `path` (the beamtime folder) and ingest status. Loads, samples and exposures carry `setup_id`; resolve a file's folder or pattern through the exposure's setup (`exposure_setup`, `integration_pattern_for_exposure`), never through the experiment. Dedup keys are per setup (`exposures(setup_id, filename)`). The New-experiment funnel sets them (`/api/fs/preview`, which lists every setup under the picked folder, then one `POST /api/experiments` for the beamtime with all its setups; `/api/fs/manifest` recounts a setup the user corrected); `PATCH /api/experiments/:id` edits only `name` and `description`. There is no `experiment.toml`.


Read `docs/experiment-config.md` before touching the funnel (`routes_fs.jl`), experiment create/scan (`routes_experiments.jl`, `ingest.jl`), or `config.jl`.

## Filesystem + DB layout

- **Read-only experiment directories at runtime.** Himalaya never creates, modifies, or deletes any file inside an experiment dir during ingestion (`scan_and_group!` / HTTP scan), `analyze`, or `serve`.
- **Central DB.** All CLI commands open the same DB resolved by `default_db_path()` in `db.jl`: `HIMALAYA_DB_PATH` if set, else `~/.himalaya/himalaya.db` (parent auto-created). One DB stores every experiment; experiment dirs are pure read-only data sources. Tests pass an explicit file path (`open_db(joinpath(tmp, "himalaya.db"))`) for isolation.
- **One exposure per image.** `scan_directory` enumerates images in `data_dir` by `image_pattern`, and builds each metadata and integration path by putting the stem into its pattern. When debugging "exposures missing" or "no peaks after a scan," run `GET /api/fs/manifest` with the setup's `data_dir` as `path`, its `analysis_dir`, and its patterns (without `analysis_dir`, every stem is reported as missing its integration file): its `unmatched` list names each stem missing a sidecar, with near-miss filenames.

## Image route

- **Detector TIFFs are Q0f31 fixed-point.** TiffImages loads as `Gray{Q0f31}` (= `Fixed{Int32, 31}`). `Float32.(channelview(raw))` divides raw photon counts by 2³¹ (~2.1e9), making `log1p` a numerical no-op (~4.7e-10 per count). To recover photon counts, use `reinterpret.(Int32, channelview(raw))`. Then `max(., 0)` clips beamstop/dead-pixel negatives, `log1p` compresses, and a p99-of-positives clip prevents the direct beam from crushing diffraction-ring contrast. See `image.jl::load_and_lognormalize`.
- **`Cache-Control: private, max-age=31536000, immutable`** on `routes_exposures.jl`'s image route. The frontend appends `?v=<image_version_token>` (= `IMAGE_PROCESSING_VERSION` + TIFF mtime), so the URL itself is the cache key — a TIFF rewrite or a `IMAGE_PROCESSING_VERSION` bump changes the URL and forces a refetch. Bump the version const (image.jl) whenever rendered bytes change; never lengthen the max-age without keeping the `?v=` invalidation intact.
- **Thumb disk cache (issue #261).** `?thumb=1` requests go through `ensure_thumb_cached(db, exposure_id, path)`, which returns `(bytes, raw_h, raw_w)` like `ensure_full_cached` — a `<db_dir>/cache/thumb-128/{id}-{token}.png` cache with a `.size` sidecar holding the raw detector size, so a cached thumb answers `X-Image-Width`/`X-Image-Height` without opening the TIFF (a thumb cached before the sidecar existed reads the size once and writes it), where `token = image_version_token(path)` so a version bump or TIFF rewrite naturally re-keys (stale entries are left, never read). Guarded on `db.file == ":memory:"` (renders fresh, no write) so in-memory test DBs work unchanged. The thumb path uses `load_and_lognormalize_thumb` (downscale-BEFORE-lognormalize) — a triage preview, NOT the science view; a faint narrow ring may under-render. `prewarm_thumbnails!(db; threads, experiment_id)` populates the cache after each successful `run_ingest!` pass: `prewarm_after_ingest!` spawns it on its own task with its own background connection, after `ingest_complete`; it is spawned before the ingest lock is released so tests can find it, but never holds that lock. It is single-threaded, so it takes one of the request threads (`:default` pool) rather than all of them; a second warm for the same experiment waits for the first. It records the task in `THUMB_PREWARMS[experiment_id]`; tests call `wait_prewarm(id)` after any `run_ingest!` so no warm outlives its temp dir, and `_THUMB_PREWARM_GATE` lets a test hold the warm to observe the order. It is skipped for a DB with no cache dir (`:memory:`). A cached entry is skipped without a read, so a warm doesn't bump LRU. The workspace never waits on thumbnails; an un-warmed one renders on first view. `scan_and_group!` itself no longer warms, and the progress bar has no thumbnails stage. Workers are FS-only — never touch the DB connection inside the `@threads` loop, and a per-row `try`/`catch` keeps one undecodable TIFF from aborting the whole `@threads` batch. **The ingest call is scoped `experiment_id=`.** Unscoped it walked every exposure in every experiment on every scan (O(corpus) per ingest, and a long silent tail with the progress bar pinned at 100%); scoping by *experiment* rather than by the ids just inserted is deliberate — it preserves the repair path, so a thumbnail that failed to warm gets another attempt next scan. A TIFF rewritten within the same second as its render keeps its token, so the stale thumbnail stays; re-rendering every exposure on every scan to close that hole is not worth it.
- **`X-Image-Width`/`X-Image-Height` are read by the browser from the same origin.** The frontend's ring overlay reads them with `fetch` (`getDetectorSize` in `frontend/src/api.ts`). Same-origin today (Oxygen serves `dist/`, and Vite proxies `/api` in dev). If the API is ever served cross-origin, the image route must add `Access-Control-Expose-Headers: X-Image-Width, X-Image-Height, X-Image-Version`, or the browser hides them and every ring silently disappears.
- **Full image disk cache.** The full route goes through `ensure_full_cached`, which keeps the 1536 px PNG in `<db_dir>/cache/full-1536/{id}/{token}.png` with the raw detector size in `{token}.size` beside it (the ring overlay's `X-Image-Width`/`X-Image-Height` need it on a hit, and a hit must not open the TIFF). The size is written before the PNG, a hit needs both, and an unreadable entry renders again. A miss deletes that exposure's other-token entries, because at 0.5–2 MB per frame (about 100× a thumb) stale copies from a version bump or TIFF rewrite would fill the disk. The whole `cache/` directory is capped at `IMAGE_CACHE_CAP_BYTES` (1 GiB) and evicts least recently viewed first, thumbs and full frames alike (a thumb re-renders in a few ms). A hit, thumb or full, bumps the PNG's mtime through the open handle (never `touch(path)`, which would recreate a file eviction just removed; a failed bump only costs LRU accuracy). The byte total lives in `_CACHE_BYTES`, seeded by one scan per process and updated by full-frame writes. Thumb writes don't update it, so the cap can overshoot by the thumbs written since the last scan, which corrects it. Crossing the cap scans once and evicts down to 90%, never the frame just written, and removes temp files older than an hour. Writes and eviction share `_IMAGE_CACHE_LOCK`, so a miss never races an empty-directory removal. The precompile workload saves and restores `_CACHE_BYTES`. Same `:memory:` guard and token keying as the thumb cache. Nothing prewarms it; a render costs ~60–100 ms, so the first view of each frame pays once.

## Exposure-state quirks

- **What a sample analyzes is its selection** (docs/image-selection.md). `exposures.deselected` stores it, and `analyzed_exposure_id` (`analyzed_exposure.jl`) resolves it to the one selected image or to the `kind = 'combined'` average of exactly the selected set (`combine.jl`, one row per distinct set, never deleted). Never average implicitly, never pick a "newest kept" image, and run `refresh_selection!` after any write that changes kept or selected images. `select_exposure` log rows replay as a retired kind.

## Phase-type serialization

- `string(Himalaya.Pn3m)` returns the fully-qualified `"Himalaya.Pn3m"`. When storing phase names in SQLite, use `string(nameof(P))` → `"Pn3m"`.
- The inverse is `getfield(Himalaya, Symbol(name))` (always validate with `P isa Type && P <: Himalaya.Phase` before calling `phaseratios`).

## Anti-patterns

- **Ingest progress frames carry TWO orthogonal discriminators — `phase` and `stage` — do not conflate them.** `phase` (set by `run_ingest!`: absent until the first pass completes, `"rescan"` after) selects the workspace status line's wording: absent → "Reading files…", `"rescan"` → "Checking for new files…" until counts arrive. `stage` (set by `scan_and_group!`: `"discovery"` / `"analyzing"`) names the stage in the status line ("Analyzing 5 of 1,200", labels in `frontend/src/lib/ingestStages.ts`). `on_progress` is `(processed, total, stage)` and each stage reports against its OWN denominator. A frame with no `stage` reads "Ingesting N of M", and the samples invalidation still fires.

- **Read beamtime folders through `dir_entries.jl` (`list_names`, `folder_names`, `any_name`), never `readdir`.** Base's `readdir` holds up garbage collection for as long as the directory read takes, so on a slow network share one listing stalls every thread that allocates: the ingest, and every request. That's why folder suggestions crawled during an ingest. `dir_entries.jl` makes the libuv calls `gc_safe` (as Base already does for `stat`), `folder_names` takes entry types from the directory read instead of a stat per entry, and `any_name` reads in batches and stops at the first match. `test_routes_fs.jl` fails on a `readdir`/`walkdir` anywhere in `src/` except `image.jl`, whose render cache sits on the server's own disk.
- **`scan_directory`'s per-file loop is the expensive half of an ingest, not `readdir`.** Per exposure it does two `isfile` stats plus a full `parse_prp` — three round trips × N over SMB. It reports `on_progress(i, n, "discovery")` because it used to run entirely silent, leaving the UI with no denominator until it finished. Related: `derive_geometry` has a **pre-parsed** method taking `parse_prp` NamedTuples; the ingest paths pass `m.prp` from the metas so the PRPs are not read a second time (the path-based method re-parsed all of them — a second full pass per ingest). Only the funnel preview (`routes_fs.jl`), which has paths and no metas, uses the path-based method.

- **An evicted SSE subscriber's channel MUST be closed, not just dropped from `SSE_SUBSCRIBERS`.** All fan-out goes through `_fanout_frame!` (events.jl); `_try_put!` returning false means the subscriber is closed or saturated, and `_fanout_frame!` then both un-registers it *and* `close(sub.pending)`. Dropping it alone leaves the `/api/events` handler parked on `for frame in pending` (server.jl) forever — the HTTP response never finishes, so the browser's EventSource sees a healthy socket, never fires `onerror`, and never auto-reconnects; the client goes permanently deaf to *every* curation event until a reload. `docs/event-log.md` §"SSE" already specified this behavior ("a pruned subscriber reconnects on the EventSource side and gets a fresh subscription") — the doc was right and the code was wrong. An ingest scan is the reliable trigger (it out-runs the 64-slot channel). Any new broadcaster must call `_fanout_frame!` rather than hand-rolling the subscriber loop.

- **No route may INSERT/DELETE into `peak_curations` or `index_group_members` except through `apply_event!`.** It is the sole writer to view tables.
- **A peak is `(source, id)`, never a bare id.** `auto_peaks` and `peak_curations` are separate AUTOINCREMENT sequences that both start at 1, so on any real DB a manual peak and an auto peak in the same exposure share an id (curation ids are also spent by excludes). Peak routes carry the source in the path (`PATCH /api/peaks/auto/{id}`, `DELETE /api/peaks/manual/{id}`), and `index_peaks` carries `peak_kind`. A new route or query that takes a peak id must take its source too. Tests that touch both sources should make the ids collide (`align_next_curation_id!` in `test_fixtures.jl`) rather than rely on hand-picked distinct ids. One path still takes bare ids: `POST /api/exposures/{id}/speculative` (`anchor_peak_id`, `additional[].peak_id`). It resolves each id's kind with `_kind_for`, which prefers `auto_peaks`, so a manual peak that shares an id with an auto peak cannot be anchored there. No UI calls it today (only a rehydrated `speculative_created` op still sends it); give it a source before anything new does.
- **From inside `with_idempotency`, call `apply_event!(InTransaction(), …)`** — never the public `apply_event!(db, req; …)`. The public method opens a nested savepoint AND broadcasts immediately, bypassing the post-commit queue. See `docs/event-log.md` §3a + `docs/mutation-queue.md`.
- **Experiment dirs are read-only at runtime.**

## Comments are ratcheted

Every tracked Julia file is covered by the comment ratchet, backend `src/`, `test/`, `scripts/` and `bench/` included, and one-line `"…"` docstrings count (`make lint`, or `npm run lint:ratchet` in `frontend/`). Agents don't write comments: put the reason in a name, a small function, a type, a test or an assertion, because comments go stale and code doesn't. Allowed: comments starting with `# physics:`. A backend-only change still has to pass `make lint`. See CLAUDE.md "Conventions" and `frontend/src/AGENTS.md` "Ratchets".

- **Peak model training service (`peak_models.jl`, `peak_training.jl`, `peak_training_service.jl`; design in `docs/peak-model.md`).** The server never trains in-process: a due check (`peak_training_due`, from the `peak_models` watermark and `user_actions`) spawns `himalaya train-peak-model --db <file>` as a child (`Base.julia_cmd()`, so it inherits the sysimage), which opens the database read-only, evaluates the gate out of fold and prints one JSON object; the server records it as a `peak_models` row under `_DB_WRITE_LOCK` (`failed` with the stderr tail on a crash). HimalayaUI source is comment-free (the ratchet counts docstrings), so the reasoning lives in the design doc. Tests replace `PEAK_TRAINING_COMMAND` with a fake and boot with `resume = false` (no timer); call `stop_peak_training!()` in a `finally` so no child or timer outlives the test. The feature cache is `<db dir>/cache/peak-features/<db stem>/`; the child, not the server, writes it. Tests that call `boot!` with the default `resume = true` start the training timer and must call `stop_peak_training!()` in their `finally`.
- **Model-written peaks (`peak_model_detect.jl`, `peak_model_pass.jl`, resolver and promotion in `peak_models.jl`; design in `docs/peak-model.md`, "Model-written peaks (step 4)").** `analyze_exposure!` is the only code that detects peaks. It always runs the hybrid, then, for an exposure with `reviewed_at IS NULL`, the active model from `production_detector(db)` (one query per call, parsed model cached per database file by id), and passes `found_by` and `model_id` explicitly to `diff_update_auto_peaks!`. It sets `exposures.peak_model_version` (never on the wire, never in `analysis_version`, so no ingest query or `ingest_has_work` sees a promotion). Never call `findpeaks` for stored peaks anywhere else. The model pass calls it with `force_detect`, `only_unreviewed` and `log_event = false` (no `user_actions` row, still an `analyze_run` frame with `id` 0). Pass concrete `String`s to `JSON3.read` when loading stored models: an `AbstractString` call made the precompiled analysis and edit-route code recompile on first use. Tests replace `PEAK_MODEL_PREDICT` (restore it in a `finally`), set `PEAK_MODEL_PASS.stopped = false` before starting a pass and call `stop_peak_model_pass!()` after it; `stop_test_server!` stops it too. Tests that promote a model (a real `passed` run) start a pass.
